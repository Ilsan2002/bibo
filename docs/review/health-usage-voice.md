# Health, usage statistics, website tracking and voice review

Scope: `HealthScreen`, `HealthParser`, `DayReview`, `StatsScreen`, `UsageCharts`, `UsageRepo`, `WebsiteRepo`, `WebTracking`, `VoiceParser`, `SmartVoiceParser`, `HoldToTalkButton`, `Haptics`, and relevant theme/Room/manifest/caller contracts. No `AGENTS.md` found under `/workspace`. This review changes no app source. The app attempts to turn everyday activity into a personal daily record: observed app/browser use, manually/verbally logged activity, four health habits, food estimates, and a narrative summary. Trustworthy records, recoverable edits, and predictable interactions are the central product requirements.

Evidence: source review plus executable JVM probes. `VoiceParser.kt` was compiled unchanged into an external harness; the health fallback method/types/regex table were copied directly from current source (excluding Android/model branches) and executed. DST arithmetic uses the same JDK time operations as `UsageRepo`. `check_health_usage.py` demonstrates the reviewed stale-copy/SQL/merge transitions in an isolated in-memory database; it does not execute Android UI. Results are in `health-usage-voice-probes/results.txt` and `state-results.json`. Root reproduced the accessibility-service constructor crash on the Android36 emulator; evidence is `accessibility-crash.log`, and prior accessibility settings were restored. Browser OEM/recognizer/model behavior remains device-dependent.

## Ranked findings

### HV01 — P1: enabling the accessibility service can crash its constructor, disabling two features

**Action:** Enable Bibo's accessibility service from Stats, or enable it to block apps during focus. **Expected:** service starts and samples browser use/enforces blocking. **Actual:** `WebTrackingService` initializes `systemPackages` with `packageName` before Android attaches its base context. `ContextWrapper.getPackageName()` requires that attached context, so construction throws a null-base-context exception. Root reproduced `Unable to create service com.bibo.data.WebTrackingService`, caused by `ContextWrapper.getPackageName()` null-base-context NPE on Android36, including restart failure; see `accessibility-crash.log`. **Refs:** `data/WebTracking.kt:113–116`, `AndroidManifest.xml:104–114`. **Impact:** website tracking and focus protection both fail because they share this service; UI checks the enabled setting rather than live readiness and may still say enabled. **Confidence:** high, reproduced in installed APK on Android36 and supported by source. **Fix:** initialize context-dependent values in `onCreate/onServiceConnected` or lazily after attachment; expose actual service readiness/errors. **Regression:** fresh enable, process recreation, reboot, permission revoke/regrant, and focus activation all start one live sampler without constructor crashes.

### HV02 — P1/P2: URL-bar lookup lacks the required resource-ID reporting flag

**Action:** After a functioning service starts, visit Chrome/Firefox/Samsung Internet sites. **Expected:** domain-specific time. **Actual:** `findAccessibilityNodeInfosByViewId` requires the view IDs to be reported, but the accessibility configuration only requests `flagRetrieveInteractiveWindows` and omits `flagReportViewIds`. Android's contract makes URL-node lookup unreliable/empty even though permission appears enabled. **Refs:** `res/xml/web_tracking_service.xml:4`, `data/WebTracking.kt:265–268`. **Confidence:** high API contract; browser-specific runtime not exercised here. **Fix:** request report-view-IDs and verify supported browser IDs using real nodes; display unsupported/unavailable sampling state separately from no browsing. **Regression:** known URL with toolbar visible is found in each supported browser; hidden toolbar, updates, unsupported browsers, and restricted settings show an honest status.

### HV03 — P1/P2: combined habit taps silently overwrite each other

**Action:** On an unlogged day, quickly tap Showered and Clean clothes; alternatively, log a habit by voice while toggling another. **Expected:** both changes persist. **Actual:** every tap copies the entire displayed `HabitDay` snapshot, then asynchronously upserts that row. Both taps can copy all-false state before the first Room emission; the second row replaces the first change. Voice uses a separate read/copy/upsert with the same lost-update possibility. **Refs:** `ui/HealthScreen.kt:106–108,128–136,158–165`, `data/Db.kt:281–289`. External state probe reproduces shower false/clothes true after the two copies. **Impact:** exactly the user's “combine a few things and the other thing stops working” pattern, with undetected corruption of the daily record. **Confidence:** high, deterministic interleaving; UI timing reproduction not performed. **Fix:** field-level atomic updates or a serialized repository transaction that reads current state inside the write operation; define explicit SetHabit rather than stale whole-row replacements. **Regression:** concurrent different-field taps retain both; two same-field toggles have defined parity; voice/manual races, rapid date changes, rotation and process recreation preserve the intended day and state.

### HV04 — P1/P2: asynchronous food logging changes its target day after the user navigates

**Action:** Begin “add food”/voice parsing on day A, then select day B before Nano parsing or a background write finishes. **Expected:** save on day A, with completion saying which day received it. **Actual:** the coroutine reads mutable `epochDay` only after the parser returns, and again inside a separately launched write. Food insertion and habit retrieval can therefore use the new day. The target can even change between operations. **Refs:** `ui/HealthScreen.kt:139–165`. **Impact:** meal totals/habits go to the wrong day and may contaminate Mentor context. **Confidence:** high source-proven capture bug. **Fix:** capture `targetEpochDay` and input before launching; write one transaction via a durable operation; render completion against that immutable identity. **Regression:** slow parser plus day navigation, parse crossing midnight, multiple concurrent logs for different days, leaving/reopening the tab.

### HV05 — P2: logging reports success before durable writes, and a multi-item log is not atomic

**Action:** Add a meal with several items/habits; immediately leave the screen, or encounter an insertion failure. **Expected:** all intended items persist once, with saving/error state and retry. **Actual:** the composable-scope coroutine performs parsing first, so leaving cancels work before durable AppScope writes even start. Once launched, writes are separate inserts/upsert without a transaction; the UI confirms immediately without awaiting them. An exception can leave half a meal while the user already saw “Logged.” `AppScope.io` has SupervisorJob but no exception handler (`data/AppScope.kt:19–20`); uncaught launch failures are not converted into a user result and may reach Android’s fatal exception handler. Repeated presses have no busy state/deduplication. **Refs:** `ui/HealthScreen.kt:97,139–173,300,323`, `data/Db.kt:296–307`. **Confidence:** high source proof; DB failure not injected. **Fix:** repository SaveHealthLog operation with a transaction, immutable operation ID and result; persist/own accepted work independently of navigation; show saving then confirmed/failed with retry. **Regression:** leave during inference, duplicate submit, exception on second item, write failure after parse, process death and recoverable resubmission.

### HV06 — P2: the fallback health parser creates confident false records for common language

**Action and reproduced outputs:** `had green tea` produces Green tea **and** Tea: 4 kcal/77 mg caffeine rather than one 2 kcal/30 mg estimate; `I did not eat pizza` logs 285 kcal; `had two coffees` and `had two bananas` log nothing; `I will go to the gym tomorrow`, `training a model`, and `I ran late for work` mark worked-out true; `didn't drink coffee but showered` logs coffee and marks showered false. **Expected:** respect negation, quantity, tense and the clause containing the habit; ask/preview uncertain interpretations. **Cause/refs:** whole-text independent keyword matches, overlapping FOOD_TABLE entries, missing plurals/quantities, broad stem regex and negation searched in the previous 24 characters: `ui/HealthParser.kt:98–145`. Nano output also accepts unrestricted negative/unbounded nutrition and converts malformed nonboolean fields to false (`66–93,150–151`). **Impact:** core health record/AI feedback is wrong on ordinary phrases, especially devices where Nano is unavailable. **Confidence:** high executable reproduction of unchanged fallback logic; Nano malformed-response branch source-proven. **Fix:** structured normalized draft with one food entity per mention, quantity/serving and finite nonnegative bounds, clause-local negation/tense, parser provenance/confidence; editable confirmation. Explicit manual item entry should always work. **Regression:** overlapping food names, plurals, quantities, mixed positive/negative clauses, future/conditional speech, unrelated train/run words, unsupported foods and malformed model data.

### HV07 — P2: clock-only voice results destroy dates, overnight ranges and durations

**Executed actual source:** at noon `from 9 to 10pm` gives 09:00–22:00 (13h); `from 23:00 to 01:00` gives 23:00–23:30 (30m); at 00:15 `for the last 30 minutes` gives 00:00–00:15 (15m); `for 0 minutes` at noon gives 00:00–12:00; `for 1.5 hours` falls through to a future 30m block. In PLAN mode `gym 3pm` typed at 20:00 gets 15:00–20:00, using elapsed time for a planned event. **Refs:** `ui/VoiceParser.kt:35–73,93–109,133–179`. `ParsedLog` contains only LocalTime (`5`); Nano fallback “repair” loses explicit overnight intent (`SmartVoiceParser.kt:80–90`); ML Kit strips the extracted dates and sorts times (`94–117`); the calendar caller always assigns `LocalDate.now()` (`CalendarScreen.kt:266–273`). “Yesterday”/“tomorrow” cannot survive any parser that returns only times, and a voiced log on a historical page jumps to today. **Expected:** preserve stated dates and actual interval length, inherit common suffix meridiem sensibly, distinguish plan defaults from log defaults, and ask/preview unresolved ambiguity. **Impact:** records can be off by many hours/day; source engines disagree depending on device/model availability. **Confidence:** high executable/source proof. **Fix:** shared temporal parser returns ZonedDateTime/instant interval plus explicit day, timezone, interpretation/provenance and confidence; zero/negative durations rejected; retain mention ordering; avoid silently replacing invalid explicit ranges. **Regression:** shared am/pm suffix, explicit overnight, midnight duration, yesterday/tomorrow, viewed day, zero/fractional/large duration, DST overlap/gap and same phrase across all engines. Coordinate with calendar editor's separate equal-time/next-day/save rules.

### HV08 — P2: voice fallback can hang indefinitely and ignores cancellation

**Action:** Use voice when Nano is unavailable and ML Kit's entity model has not downloaded, particularly offline. **Expected:** a bounded parse and quick deterministic fallback with progress/cancel. **Actual:** every entity parse calls blocking `Tasks.await(downloadModelIfNeeded())`, then another unbounded `Tasks.await(annotate())`; a suspend function does not make these waits cancellation-aware. No timeout or progress appears in the caller. Catching every Throwable treats cancellation as a reason to continue to more parsers. Fresh clients are never closed. **Refs:** `ui/SmartVoiceParser.kt:40–43,58–60,94–120`; `HealthParser.kt:50–51`, `DayReview.kt:80–81`; `CalendarScreen.kt:264–275`. **Confidence:** high source proof; model download stalls not induced. **Fix:** prewarm reusable extractor, cancellation-aware Task await, deadline per engine, explicit fallback status, rethrow CancellationException and close clients. **Regression:** never-downloaded model offline, stalled download, tab departure/cancel, timeout fallback, rapid repeated input, device lacking Nano.

### HV09 — P2: microphone cancellation, errors and rapid reuse have no coherent state machine

**Action:** Hold/speak then drag away; press again while recognition is still finishing; revoke microphone permission in Settings; use a device without speech recognition. **Expected:** cancellation discards speech, one active request, actionable errors and permission recovery. **Actual:** `tryAwaitRelease()`'s false/canceled result is ignored and `stopListening()` still submits results. No recognition-session ID/busy guard stops stale callbacks from affecting a new press; `onError` silently forwards any partial transcript as final (which Daily immediately writes). Unsupported recognizer presses silently do nothing; permission is only remembered initially/from the prompt, not rechecked on resume. `startListening` has no error handling, recognizer stops only by gesture/disposal and has no lifecycle pause cancellation. **Refs:** `ui/HoldToTalkButton.kt:52–107,121–134,172–202`. **Confidence:** high source proof; recognizer-specific callback order not simulated. **Fix:** Idle/RequestingPermission/Listening/Processing/Error states with session tokens, explicit cancel on canceled gesture/background, disable/reuse only after terminal callback; never silently commit an errored partial; errors with retry/manual-entry. **Regression:** drag cancellation, double press, stop-before-ready, natural recognition end while finger held, old callback after new session, no recognizer, denied/revoked permission, offline/timeout.

### HV10 — P2: “on-device only” speech claims disagree with the recognizer implementation

**Action:** Speak a calendar/health log expecting the README's on-device SpeechRecognizer guarantee. **Expected:** on-device speech, or an accurate disclosure that speech provider/network recognition may be used. **Actual:** standard `createSpeechRecognizer` is used, explicitly prefers Google's service and intentionally does not request offline recognition. This permits network recognition by the provider; it does not prove every request is transmitted. **Refs:** `ui/HoldToTalkButton.kt:167–202`, README Tech/Permissions; `SmartVoiceParser.kt:26` describes parsing as local but cannot extend that guarantee to preceding STT. **Impact:** health/activity speech may cross the trust boundary described to the user. **Confidence:** high implementation/disclosure mismatch; actual transmission not inspected. **Fix:** use `createOnDeviceSpeechRecognizer` after capability check for the local guarantee; clearly explain any network fallback before choosing it, and provide text entry. “Prefer offline” alone is not an on-device guarantee. **Regression:** no on-device engine, installed Google/default providers, airplane mode and verified selected engine.

### HV11 — P2: usage ingestion is a nontransactional read side effect with concurrent inconsistent consumers

**Action:** Open Stats with fresh/changed usage data; rapidly change dates while ingestion runs. **Expected:** headline, trend and heatmap use one committed snapshot. **Actual:** three independent produceState coroutines call ingestion. The first sets static `lastIngest` before work completes; others skip ingestion and can read old data, or the empty/partial window after delete but before insert. Prune/delete/upsert are separate calls. Navigation cancellation/failure after delete can leave missing records, and throttle then prevents an immediate repair. Results are one-time reads, so a chart may stay stale until another refresh. **Refs:** `data/UsageRepo.kt:156–168,175–247,249–254`, `data/Db.kt:240–255`, `ui/StatsScreen.kt:113–129`. **Confidence:** high source-proven interleaving; scheduler timing not reproduced on UI. **Fix:** app-scoped ingestion Mutex/operation shared by all callers; transactionally replace and mark completion only on success; expose a Flow of committed snapshots and load one StatsState. **Regression:** simultaneous totals/chart/calendar requests, cancel between deletion/insertion, query failure, rapid date navigation, refresh inside throttle window, and first-time empty database.

### HV12 — P2: measured usage is distorted by display merging, window boundaries and missing coverage

**Action:** Switch away from an app for 20s then return; reopen Bibo after four days; inspect a moving 48h boundary. **Expected:** observed active durations only, historical gaps labeled unknown. **Actual:** gaps <=30s are merged into sessions whose entire bounding duration is counted in all stats. Two 60s visits separated by 20s become 140s instead of 120s. `rawSessions` begins with an empty open map and cannot carry sessions already foreground before query start. A previously persisted merged interval starting before the moving boundary survives `deleteFrom`, while newly reconstructed inner intervals can be inserted overlapping it (isolated SQL probe: expected merged140s, sum200s). Ingestion only runs on usage reads and queries the last48h; no worker/other caller keeps collecting older available system history, so several unopened days show zero. **Refs:** `data/UsageRepo.kt:91–127,133–168`, `data/Db.kt:254–255`, callsite search finds only Calendar/Stats. **Confidence:** high arithmetic/source proof; long device history not exercised. **Fix:** separate raw accurate interval storage/aggregate calculation from gap-merged timeline display; carry boundary state with overlap/lookback; replace overlapping windows without duplicating old fragments; ingest since persisted watermark as available and track coverage/missing-history explicitly. **Regression:** app switches with1/20/31s gaps, session crossing ingestion boundary, two rapid same-app activity resumes/pauses, unopened>48h, revoked usage access, reboot/screen off and split-screen. Decide whether “screen time” means union of visible time or aggregate per-app foreground time; currently concurrent apps can double-count the headline.

### HV13 — P2: heatmap is wrong on DST days; its totals can disagree with the headline even without DST

**Action:** View spring/autumn clock-change day; use three apps for30s each. **Expected:** bins partition actual intervals, with skipped/repeated hours handled; daily totals consistent. **Actual:** each hour is separately converted to a zoned instant then given a fixed3600s width. On New York 2026-03-08, hours2/3 are the same instant range:23h real day can sum24h. On2026-11-01 the repeated hour is omitted:25h can sum24h. `queryTotals` drops every app below60s while `dailyTotals/hourlyMatrix` sum all cached intervals; three30s apps yield headline0 versus weekly90s. **Refs:** `data/UsageRepo.kt:191–230,239–244`, `StatsScreen.kt:138,175–179`. **Confidence:** high executable arithmetic. **Fix:** iterate real instants over each day's zone-correct boundaries and map to labelled hour bins (aggregate both repeated hours or show both explicitly); compute total independently of list threshold and group hidden brief uses as Other. **Regression:** DST gap/overlap in multiple zones, 23/25/normal days, zone changes, short-app total thresholds, headline=hour-bin/weekly totals under a defined metric.

### HV14 — P2: browser sessions can include hidden/locked/off-screen time and be attributed to the wrong site

**Action:** Browse site A, go to a search/new-tab page or a browser without a valid toolbar domain, hide toolbar, lock screen, or leave for an inaccessible window. **Expected:** record only confirmed visible website time and stop while locked/off-screen. **Actual:** invalid/null URL keeps previous `currentDomain`; null active root returns without closing; no current browser identity is stored. A browser switch to unsupported URL state can extend siteA. Screen-off only commits once, while the recurring sampler remains active and has no interactive/keyguard guard, so stale browser roots can restart sessions during screen-off. These failure paths are likely device/OEM dependent. Records are held only in memory until a change/exit/off event, so process kill can lose a long visit; writes use `runCatching` and errors are silently discarded. The website DAO defines `pruneBefore` but no application caller invokes it, so browsing history grows indefinitely with no in-app deletion/retention control (`data/Db.kt:354–355`). **Refs:** `data/WebTracking.kt:106–108,120–160,257–289`. **Confidence:** high state-machine omission, medium for exact OEM sampling behavior. **Fix:** explicit ForegroundBrowser(package,domain,lastConfirmedMonotonicTime)/Unknown/Inactive states; interactive/unlocked lifecycle gating; expire uncertain samples rather than inventing certainty; durable/checkpointed sessions with recoverable DB errors. **Regression:** hidden toolbar, search/new tab, browser switching, notification shade/keyguard, root null, screen-off heartbeat, service recreation, clock change, failed insert. Offer independent tracking pause/clear history; an enabled service currently also implies tracking whenever focus needs that shared permission.

### HV15 — P2/P3: stale/failed/unknown states look like accurate empty data; day-review navigation wastes work and blocks other dates

**Action:** Switch dates during load or day-review generation; stay open across midnight/time-zone change; revoke access; inspect an unobserved day. **Expected:** selected date's data, loading/error/coverage states, stable target day. **Actual:** Stats uses initial empty values and retains old produceState values until replacements arrive, so today's totals can temporarily appear under yesterday's header; no catch/error/retry surrounds stats IO. Refresh occurs only on resume, not live while the page remains open. Zone is remembered once and selected today does not follow a ticking day. Health's `reviewing` is not keyed/canceled by day, so generating on A then selecting B keeps B's Generate button disabled until A finishes. The coroutine captures A's `review` MutableState delegate; because `remember(epochDay)` creates a new state for B, a late result updates an abandoned A state rather than displaying A's text on B. Thus work/results are lost on navigation; the prior wrong-day-visible-text assertion was overstated. The generated day is still read from the shared `epochDay` delegate when the IO block starts (a small pre-start race), and failures have no finally reset. Compiled bytecode confirms separate captured `$review$delegate` and shared `$epochDay$delegate`/`$reviewing$delegate`; see `health-usage-voice-probes/review-capture-bytecode.txt`. Habit/food flows similarly retain old emissions until their new day arrives; immediate toggles can operate on a previous day's `HabitDay`. Cached website/usage records are hidden when permission is disabled even though permission should only gate collection. **Refs:** `StatsScreen.kt:71–82,85–107,113–136,228–240,332–338`; `HealthScreen.kt:102–126,128–136,257–265`. **Confidence:** high source/compiled closure proof; exact retained emission window depends scheduling. **Fix:** ViewModels with selected-day keyed state and request IDs, explicit loading/error/stale/partial coverage, captured day for review, finally/cancel handling, application Clock/zone/day observables, separate history read from permission-gated collection. **Regression:** slow load + day navigation, review completes after day change, reader exceptions, midnight/time-zone change, permission grant/revoke and old history access.

### HV16 — P2/P3: Daily's correction model and “missed” habits undermine record trust

**Action:** Log an estimated meal, then notice a wrong quantity/calorie number; toggle just one habit and generate a review. **Expected:** editable estimates with uncertainty, and unknown habits distinct from confirmed skipped. **Actual:** FoodRow has only Delete, no edit/undo, quantity/serving or timestamp controls; inference automatically commits. A new HabitDay defaults all fields false, and DayReview calls untouched false values “Missed,” so recording shower alone asserts workout/prayer were missed. Generic activity TIMER is labeled Focus; overlapping cross-midnight blocks are counted at full duration for each queried day (`DayReview:30–39`) rather than clipped to that day. Intake meters silently assume2000kcal/50g sugar/400mg caffeine and saturate visually without editable targets or clear over-target state. **Refs:** `HealthScreen.kt:217–219,299–300,463–491`, `HealthParser.kt:66–93`, `Db.kt:258–266`, `DayReview.kt:30–54`. **Confidence:** high source; nutrition target appropriateness is product decision. **Fix:** editable parse preview and entries, undo delete, manual exact nutrition path, estimate/provenance labelling, configurable targets or neutral totals; tri-state habit unknown/done/skipped; day-clipped and source-specific summaries. **Regression:** untouched habits never called missed, manually skipped shown correctly, meal edit/undo updates totals/summary, nonfocus TIMER, cross-midnight/multiday/overlapping blocks and zero/over-target intake.

### HV17 — P2/P3: core voice/habit/chart UI is inaccessible or low-contrast

**Action:** Use TalkBack, keyboard/switch access, larger fonts or dark/light theme. **Expected:** operate voice logging and hear current habit/day/chart values with readable text. **Actual:** mic Surface has pointerInput only and an icon description; no semantic click/long-click action or recording status. Habit toggles convey done through color/weight without toggle role/stateDescription. Dot-strip days show a narrow weekday character and dots without full dates/habit summaries/selected state; heatmap color boxes have no numerical descriptions. `outline` is used for body/empty/unit text: dark outline#4A536A on background#0B0D12 has2.53:1 contrast; light outline#7B8090 on#FAF8F5 has3.71:1. Light primary#E2521F with onPrimary white is3.85:1, below4.5:1 for ordinary small button text. Charts/weekly strips use small fixed cells and no drill-down exact values. **Refs:** `HoldToTalkButton.kt:110–163`, `HealthScreen.kt:370–449,478–490`, `UsageCharts.kt:56–97,124–153`, `theme/Theme.kt:37–38,70,77–79,105`, `StatsScreen.kt:236–238`. **Confidence:** high source/contrast computation; full assistive-device/font-scale run pending. **Fix:** alternate tap-start/tap-stop with semantic action; toggleable/check semantics and explicit state; chart text summary/detail including dates/hours and exact duration; use onSurfaceVariant for text and adjust interactive palette contrast. **Regression:** TalkBack completes daily log and toggles habits, focus order, selected day and loading/recording announcements, 200% font scale, narrow width, theme contrast and noncolor interpretation.

## Architecture and product direction

1. Give each record a clear contract: planned activity, completed activity, observed app interval, estimated food entry and explicitly reported habit are distinct facts with source/provenance. Share typed interval/day handling across the calendar, stats, logging and summaries. Define unknown/partial coverage explicitly; an empty sample is not “zero use” or “missed.”
2. Move accepted commands into repositories/use cases (`SetHabit`, `SaveHealthLog`, `IngestUsageWindow`, `GenerateReviewForDay`) with immutable target IDs/day, atomic transactions and observable results. Screen ViewModels should own day-keyed load/draft state, and source-of-truth Flows should update after writes. Composables should not orchestrate conflicting durable updates.
3. Make source acquisition separate from derived display: observed accurate intervals feed shared aggregates; merged visual blocks are a presentation layer. Give usage ingestion one serialized owner/watermark and coverage metadata. Give browser sampling a lifecycle/foreground state machine and independent user tracking consent/control, even when focus also needs accessibility permission.
4. Treat speech/AI as draft interpreters, with bounded latency/cancel, reusable clients, structured validation and visible engine/provenance. Show interpreted date/range/items and let the user correct before saving. Support manual entry for everything; a fallback should not silently invent confidence.
5. Simplify Daily around “What did I do/consume today?” and make correction first-class. Show neutral totals/explicit estimates, editable entries, undo, configurable relevant habits and clear date context. Generate reviews from a captured factual snapshot and recompute/invalidate after edits.
6. Consolidate permission/status UI around capabilities: collect usage, track websites, block apps, transcribe locally/network. Read past locally stored records without requiring currently enabled collection permission. Distinguish configured, granted, live/healthy, unsupported, partial and failed.

## Suggested focused regression coverage

Domain tests should include actual parser phrase tables across all engines and interval/day/DST partition properties; repo tests should exercise simultaneous habit changes, atomic multi-item logs, ingestion cancellation/overlap and immutable target day; UI/instrumentation should cover canceled microphone gestures, stale callbacks, permission round trips, delayed async day navigation and accessibility semantics; targeted real-device checks are needed for each supported browser/provider, screen-off/lock, service recreation and folded/narrow/large-text layouts. Current review does not establish device-specific website measurement, speech transmission, or Nano model accuracy. Source files were not changed; root owns any emulator experiments and final evidence classification.
